# V12 research roadmap

Date: `2026-09-23`

This roadmap orders the work so an attractive tester curve cannot outrun the
definition and parity evidence.

## Phase 0 — event definition

Deliverables:

- exhaustive W1->H4 and D1->H1 C1/C2 event universe;
- broker-clock/session and source-hash manifest;
- range-interaction classification and ambiguity ledger;
- blind review pack for trigger primitives;
- stable parent/child IDs and schema validation.

Gate: independent reruns produce identical events and all exclusions have coded
reasons. No performance conclusion is allowed here.

## Phase 1 — no-ML structural baseline

Freeze:

- one trigger definition at a time;
- C2-extreme and trigger-structure Hard-SL variants;
- C1 midpoint and opposite-extreme destinations;
- same-M1 ambiguity handling;
- transaction-cost assumptions.

Report the complete multidimensional scorecard. Compare W1->H4 and D1->H1
without merging them merely to improve sample size.

Gate: a candidate population and its failures can be explained without reference
to future HA, outcome, or discretionary chart labels.

### Phase 1A status

The first rejection-only prototype is complete and reproducible. It passes the
ledger/audit gate but fails the V10 replacement gate: confirmation removes some
stops at a larger entry-delay cost, while trigger-SL selectivity is sparse and
era-unstable. Freeze this result; do not tune it on consumed outcomes. Any Phase
1B branch must separately predeclare causal true MSS or outside-acceptance
continuation semantics.

## Phase 2 — inherited sensor ablation

Add only predeclared observations:

- FAST/STD/SLOW HA phase coordinates;
- Wave Candle coordinates for H4 events;
- causal normalized liquidity and location coordinates;
- synchronized SMT primitives only if the paired data pass quality checks.

Use matched ablations. A sensor is useful only if it adds information beyond the
CRT geometry and remains stable across side/year/lane/era. Do not promote a
fixed threshold from consumed data.

## Phase 3 — conditional ML shadow

Use separate, calibrated heads or competing-risk models for:

- stop before C1 50%;
- C1 50% before stop;
- opposite extreme after 50%;
- conditional R and time-to-event.

Use purged walk-forward and/or CPCV with embargo, fold-level calibration, and a
frozen feature registry. Compare against simple base rates and monotone/linear
baselines before complex models.

Gate: out-of-fold predictions add stable calibration/discrimination without a
post-hoc direction, year, or threshold exclusion.

## Phase 4 — MQL5 parity and actual-tick economics

- build an event-probe indicator/script first;
- match Python event and feature ledgers;
- build the research EA only after parity;
- test actual ticks, spread, sessions, rejected orders, partial fills, and costs;
- report market-closed failures separately.

Gate: discrepancies are resolved at the event level. Tester P/L is not accepted
while candidate counts or coordinates differ from the oracle.

## Phase 5 — future shadow

Freeze the complete contract before reading new chronology. The current consumed
boundary is `2026-09-18 23:57`. GOLD# 2021 remains sealed.

The shadow must test:

- candidate frequency and ambiguity drift;
- stop and right-tail capital by lane/side/era;
- ML calibration drift;
- Python/MQL5 parity drift;
- execution failures and costs.

Gate: only a stable future result can justify a trade-authority proposal.

## Stop conditions

Pause or reject a branch when:

- it needs outcome-aware relabeling;
- candidate selection cannot be independently reproduced;
- lower stops are explained mainly by lower exposure or wider risk;
- right-tail loss dominates scalable risk improvement;
- performance depends on one side, one year, or one lane;
- ML improves AUC but not the prespecified economic action;
- MQL5 and Python cannot reach event parity;
- an external source's threshold or code cannot be legally or causally justified.

## Promotion requirements

A later trade-authority proposal must state exactly:

- candidate and entry definition;
- Parent/Child lifecycle;
- structural Hard SL and destination/exit logic;
- risk and concurrent-exposure policy;
- data/session assumptions;
- ambiguous and failed-order policy;
- evidence windows and untouched validation;
- code/model/schema hashes;
- failure modes and rollback condition.
